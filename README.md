# APP TRUST AI

공개 근거 기반 앱 개발 방식·기술적 완성도·신뢰 정보 분석 서비스

- 서비스 주소: https://app-trust-ai.vercel.app/
- GitHub 저장소: https://github.com/sojin031488-ship-it/app-trust-ai

> AI 활용 여부 자체로 앱 품질을 낮게 평가하지 않습니다.
> 분석 결과는 공개 정보에 기반한 참고 자료이며, 앱의 안전성이나 실제 개발 방식을 확정하는 인증 결과가 아닙니다.

## 1. 서비스 소개

최근 바이브 코딩으로 앱을 만드는 일이 늘어나면서, 사용자는 앱이 어떤 방식으로 개발되었고 실제로 믿고 사용할 만큼 완성도를 갖추었는지 판단하기 어려워졌습니다.

APP TRUST AI는 이러한 문제를 해결하기 위해 공개 정보를 바탕으로 AI 활용 관련 근거와 기술적 완성도·신뢰 정보를 구분해 제공하는 서비스입니다.

AI를 활용했다는 사실을 결함으로 취급하지 않고, 사용자가 앱의 개발 방식과 품질을 근거와 함께 확인하여 더 신중하게 선택할 수 있도록 돕습니다.

## 2. 핵심 원칙

- AI 활용 관련 정보와 기술적 완성도를 구분합니다.
- AI를 사용했다는 이유만으로 품질 평가를 낮추지 않습니다.
- 공개 정보가 부족하다는 사실을 낮은 품질의 증거로 해석하지 않습니다.
- 검색 대상이 불확실하면 임의로 특정 앱이라고 확정하지 않는 것을 원칙으로 합니다.
- 분석 점수뿐 아니라 판단 근거와 한계를 함께 확인하도록 설계합니다.
- 공개된 자료만 사용하며 비공개 정보 탐색이나 침투 테스트는 수행하지 않습니다.

## 3. 주요 기능과 구현 범위

### 앱 정보 분석

- 앱 이름 또는 URL을 기존 수집·분석 함수에 전달합니다.
- 선택한 App Store 앱 ID를 분석 요청에 전달할 수 있습니다.
- AI 활용 관련 신호와 기술적 완성도 관련 신호를 구분해 다룹니다.
- Supabase가 설정되어 있으면 분석 결과 저장을 시도합니다.

### Apple App Store 검색

- 공식 iTunes Search API를 사용합니다.
- 최대 50개 후보를 반환합니다.
- 앱 이름, 아이콘 URL, 개발자명, 설명, 스토어 URL 등을 반환합니다.
- 같은 앱 ID의 중복 결과를 제거합니다.
- 검색 결과만으로 분석 대상을 자동 확정하지 않고 후보를 반환합니다.

검색 API가 반환하는 후보만 다루므로 모든 앱의 검색을 보장하지 않습니다.
화면의 검색 버튼과 서버 검색 함수의 연결은 배포 환경에서 별도로 확인해야 합니다.

### Google Play

현재 제공하는 범위:

- 사용자가 입력한 Google Play URL 형식 확인
- 패키지명 형식 확인
- 패키지명을 이용한 스토어 URL 구성

현재 제공하지 않는 기능:

- 앱 이름 기반 자동 검색
- 앱 설명과 개발자 정보 자동 수집
- 실제 등록 여부 검증

### 작성자 제출·보완

- 앱 정보 제출
- 작성자 코드 발급
- 제출 번호와 작성자 코드로 내 제출 조회
- 항목별 보완 요청 확인
- 수정 내용 답변 및 보완 제출
- 제출·보완·상태 변경 이력 기록

작성자 코드는 원문 대신 해시로 저장합니다.
발급된 코드는 작성자가 별도로 보관해야 합니다.

### 심사자 기능

- 심사자 코드 인증
- 제출 목록과 상세 내용 조회
- 항목별 구체적 사유를 포함한 보완 요청
- 제출 상태 변경
- 보완 답변 확인 및 처리
- 제출 정보 기반 기존 앱 분석 실행
- 분석에 대한 심사자 판정 저장

> 위 내용은 코드에 포함된 기능 범위입니다.
> 현재 배포에서 모든 기능이 통합 테스트를 통과했다는 의미는 아닙니다.

## 4. 기술 구성과 아키텍처

- 프런트엔드: HTML, CSS, JavaScript
- 백엔드: Python, FastAPI
- 데이터베이스: Supabase
- 배포: Vercel
- 외부 자료: Apple iTunes Search API 및 공개 웹·GitHub 자료

### 주요 파일

| 파일 | 역할 |
|---|---|
| `index.html` | 사용자 화면과 API 요청 |
| `main.py` | FastAPI 서버, 분석·제출·심사 API |
| `collect.py` | 공개 정보 수집과 기존 분석 흐름 |
| `detector.py` | 분석 신호·점수와 심사자 판정 기반 보정 |
| `store.py` | App Store 후보 검색과 Supabase 저장소 |
| `submissions.py` | 제출·보완·상태 변경 업무 로직 |
| `criteria.py` | 제출 정보 확인 기준 |
| `schema.sql` | 제출 관련 테이블 생성 SQL |
| `requirements.txt` | Python 의존성 |

### 구성 흐름

브라우저의 `index.html`이 FastAPI 서버에 요청합니다.

`main.py`는 요청 종류에 따라 다음 모듈을 호출합니다.

- 분석 요청 → `collect.py`, `detector.py`
- 스토어 검색 → `store.py`의 검색 함수 연결 필요
- 제출·보완 요청 → `submissions.py`, `criteria.py`, `store.py`
- 저장·조회 → Supabase

`main.py`, `store.py`, `submissions.py`는 호환되는 버전을 함께 사용해야 합니다.

예를 들어 `main.py`가 `ST.SupabaseStore`를 호출하지만
`store.py`에 해당 클래스가 없으면 서버 시작 오류가 발생합니다.

## 5. 로컬 실행 방법

Python 3.10 이상을 기준으로 합니다.
의존성 버전은 `requirements.txt`를 확인합니다.

### 가상환경 생성

```bash
python -m venv .venv
```

### 가상환경 활성화

macOS / Linux:

```bash
source .venv/bin/activate
```

Windows PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

### 패키지 설치 및 실행

```bash
pip install -r requirements.txt
uvicorn main:app --reload
```

실행 후 다음 주소에 접속합니다.

http://127.0.0.1:8000

환경변수는 실행하는 셸 또는 배포 서비스에서 설정합니다.
`.env` 파일을 생성하는 것만으로 자동 로드된다고 가정하지 않습니다.

## 6. 환경변수

| 변수 | 용도 | 없을 때 |
|---|---|---|
| `SUPABASE_URL` | Supabase 프로젝트 주소 | DB 저장·제출 기능 사용 불가 |
| `SUPABASE_KEY` | 서버 전용 Supabase 키 | DB 저장·제출 기능 사용 불가 |
| `REVIEW_TOKEN` | 심사자 인증 코드 | 심사자 인증이 필요한 요청 차단 |
| `GITHUB_TOKEN` | GitHub API 인증 | 인증 없는 API의 호출 제한 적용 가능 |
| `ANTHROPIC_API_KEY` | 선택적 리서치·LLM 보조 기능용 설정 | 실제 사용 여부는 `collect.py`의 호출 코드 확인 필요 |

### 보안 주의 사항

- 실제 키나 토큰을 소스 코드에 입력하지 않습니다.
- 서버 전용 키를 브라우저 JavaScript에 넣지 않습니다.
- `.env` 파일은 `.gitignore`에 포함합니다.
- 로그와 스크린샷에서 비밀값을 가립니다.
- 키가 공개되었다면 파일 삭제만 하지 말고 폐기·재발급합니다.

## 7. Supabase 준비

1. Supabase 프로젝트를 생성합니다.
2. 저장소의 SQL 내용을 확인합니다.
3. SQL Editor에서 필요한 SQL을 실행합니다.
4. 코드에서 사용하는 테이블과 컬럼이 존재하는지 확인합니다.
5. 서버 환경변수에 Supabase 주소와 서버 전용 키를 등록합니다.
6. 실제 제출·조회·수정 작업으로 저장 성공 여부를 확인합니다.

사용하는 테이블:

- `analyses`: 분석 결과
- `reviews`: 분석에 대한 심사자 판정
- `submissions`: 작성자 제출 정보
- `revision_requests`: 항목별 보완 요청
- `submission_events`: 제출·보완·상태 변경 이력

제출용 SQL만으로 기존 분석 테이블까지 생성된다고 가정하지 않습니다.

`create table if not exists`는 기존 테이블에 누락된 컬럼을 추가하지 않습니다.
이미 다른 버전의 테이블이 있다면 별도 마이그레이션이 필요합니다.

## 8. Vercel 배포

1. GitHub 저장소를 Vercel 프로젝트에 연결합니다.
2. 저장소의 배포 설정과 Python 서버 진입점을 확인합니다.
3. 필요한 환경변수를 Vercel에 등록합니다.
4. 변경 사항을 커밋하고 배포합니다.
5. 배포 완료 후 메인 화면과 실제 API 동작을 확인합니다.

배포 주소:

https://app-trust-ai.vercel.app/

`Ready`는 배포 완료 표시이며 모든 기능의 정상 동작을 보장하지 않습니다.

### 상태 확인

```bash
curl https://app-trust-ai.vercel.app/api/health
```

응답 형식 예시:

```json
{
  "ok": true,
  "db": true
}
```

`db: true`는 Supabase 클라이언트가 생성되었다는 의미입니다.
테이블·권한·실제 저장 성공까지 검증한 결과는 아닙니다.

## 9. 핵심 API

다음 경로는 작성 과정에서 확인한 `main.py` 기준입니다.
서버 코드를 변경하면 이 목록도 함께 갱신해야 합니다.

| 메서드 | 경로 | 기능 |
|---|---|---|
| GET | `/` | 메인 화면 |
| GET | `/api/health` | 서버 및 DB 클라이언트 상태 |
| POST | `/api/search` | 기존 앱 분석 실행 |
| POST | `/api/batch` | 최대 10개 일괄 분석 |
| POST | `/api/review` | 심사자 판정 저장 |
| GET | `/api/stats` | 심사자 판정 기반 통계 |
| POST | `/api/submissions` | 앱 정보 제출 |
| GET | `/api/submissions/{sid}/mine` | 작성자 본인의 제출 조회 |
| POST | `/api/submissions/{sid}/revisions/{rid}/answer` | 보완 답변 |
| GET | `/api/submissions` | 심사자용 제출 목록 |
| GET | `/api/submissions/{sid}` | 심사자용 제출 상세 |
| POST | `/api/submissions/{sid}/status` | 제출 상태 변경 |
| POST | `/api/submissions/{sid}/revisions` | 보완 요청 |
| POST | `/api/revisions/{rid}/resolve` | 보완 확인·철회 |
| POST | `/api/submissions/{sid}/analyze` | 제출 정보 분석 |

### 인증 헤더

- 심사자 인증: `X-Reviewer-Token`
- 작성자 인증: `X-Author-Code`

### 분석 요청 예시

```bash
curl -X POST http://127.0.0.1:8000/api/search \
  -H "Content-Type: application/json" \
  -d '{"query":"육아기록"}'
```

`/api/search`는 기존 분석 진입점이며 스토어 검색 전용 경로가 아닙니다.

`store.search()` 함수가 존재해도 HTTP 경로가 자동으로 생성되지는 않습니다.
확인한 `main.py`에는 스토어 검색 전용 경로가 없으므로,
검색 버튼의 요청 경로와 서버 연결을 최종 제출 전에 확인해야 합니다.

## 10. 데이터 흐름

### 앱 분석 흐름

1. 사용자가 앱 이름 또는 URL을 입력합니다.
2. 대상이 불확실하면 후보를 확인하고 선택하는 흐름을 사용합니다.
3. 확정된 앱 정보를 기준으로 공개 자료를 수집합니다.
4. 개발 방식과 기술적 완성도 관련 신호를 구분해 분석합니다.
5. 결과와 근거, 불확실성을 화면에 표시합니다.
6. Supabase가 설정되어 있으면 결과 저장을 시도합니다.

후보 선택과 근거 표시는 실제 배포 화면에서 검증해야 하는 UX 기준입니다.

### 제출·보완 흐름

1. 작성자가 앱 정보를 제출합니다.
2. 서버가 작성자 코드를 발급하고 해시를 저장합니다.
3. 심사자가 제출 내용을 검토합니다.
4. 수정할 항목과 구체적 사유를 지정해 보완을 요청합니다.
5. 작성자가 제출 번호와 작성자 코드로 요청을 확인합니다.
6. 작성자가 수정 내용을 답변합니다.
7. 심사자가 답변을 확인하고 상태를 변경합니다.
8. 각 변경을 이벤트 이력에 기록합니다.

### 제출 상태

| 코드 | 의미 |
|---|---|
| `submitted` | 제출됨 |
| `in_review` | 심사 중 |
| `revision_requested` | 보완 요청 |
| `resubmitted` | 보완 제출 |
| `approved` | 승인 |
| `rejected` | 반려 |

보완 요청 확인은 작성자가 직접 조회하는 방식입니다.
이메일·푸시 알림은 별도 구현이 필요합니다.

## 11. 분석 결과와 실제 근거의 연결

분석 결과는 다음과 같은 필드를 사용합니다.

| 필드 | 의미 |
|---|---|
| `signals` | 분석에 사용한 신호와 근거 정보 |
| `ai_score` | AI 활용 관련 분석 지표 |
| `quality_score` | 기술적 완성도 관련 분석 지표 |
| `confidence` | 분석의 확신 수준을 나타내는 값 |
| `verdict` | 종합 해석 |
| `raw` | DB 저장 시 보관하는 전체 분석 응답 |

각 점수의 정확한 산정 방식과 의미는 분석 코드에 따라 달라집니다.
점수를 AI 사용 확률이나 안전성 인증 수치로 해석하지 않습니다.

분석 저장 시 `signals`와 전체 응답인 `raw`를 함께 보관하도록 구성되어 있습니다.

### 근거 해석 예시

아래는 설명용 예시이며 특정 앱의 실제 분석 결과가 아닙니다.

| 공개 근거 | 가능한 해석 | 단정하면 안 되는 내용 |
|---|---|---|
| 개발자가 AI 보조 개발을 공개 | AI 활용에 대한 공개 설명 확인 | AI 사용 앱이므로 저품질 |
| 개인정보처리방침 링크 확인 | 관련 문서 링크 존재 | 개인정보 보호 수준 검증 완료 |
| 검색 결과가 반환되지 않음 | 후보 조회 실패 또는 결과 없음 | 존재하지 않는 앱 |
| 개발 자료 부족 | 개발 방식을 판단할 근거 부족 | AI 미사용 또는 AI 사용 확정 |

최종 화면에서는 다음 항목이 연결되는지 확인해야 합니다.

- 판단 항목
- 출처 URL
- 공개 자료에서 관찰한 내용
- 관찰 내용에 대한 해석
- 해석의 한계와 불확실성

현재 모든 분석 신호에 출처 링크가 존재하거나
화면이 이를 모두 표시한다고 보장하지 않습니다.

## 12. 오판과 불확실성 처리

다음은 결과 표시 및 검증 원칙입니다.
모든 항목이 자동 구현된 기능이라는 의미는 아닙니다.

### 근거 부족

자료가 부족하면 단정 대신 다음과 같이 안내하는 것을 원칙으로 합니다.

> 공개 근거가 부족하여 개발 방식을 판단하기 어렵습니다.

자료 부족은 앱의 품질이 낮다는 뜻이 아닙니다.

### 외부 조회 실패

조회 실패는 앱이 존재하지 않는다는 뜻이 아닙니다.

안내 예시:

> 앱 정보를 불러오지 못했습니다. 잠시 후 다시 검색하거나 공식 URL을 입력해 주세요.

현재 검색 함수는 일부 요청 실패와 빈 결과를 모두 빈 목록으로 반환합니다.
둘을 화면에서 명확히 구분하려면 추가 처리가 필요합니다.

### 잘못된 앱 선택

동명의 앱은 개발자명·아이콘·스토어 URL을 확인해 구분하는 것을 원칙으로 합니다.
잘못 선택한 경우 다시 선택해 분석해야 합니다.

### 분석 해석 오류

- 점수만으로 앱 사용을 권장하거나 금지하지 않습니다.
- 심사자 판정도 객관적인 정답으로 보장하지 않습니다.
- 전용 오판 신고·이의제기 기능은 별도 구현이 필요합니다.
- 작성자 보완 기능은 제출 정보 수정 기능이며 자동 판정의 정확성을 보증하지 않습니다.

## 13. 알려진 한계

- 공개 자료만으로 실제 개발 방식과 전체 품질을 확정할 수 없습니다.
- AI 개발 흔적이 없다고 AI 미사용을 증명할 수 없습니다.
- 내부 코드·실제 성능·보안·개인정보 보호 수준을 모두 검사하지 않습니다.
- Apple 검색은 국가·검색어·외부 서비스 상태에 영향을 받습니다.
- Google Play 자동 검색과 앱 정보 수집은 지원하지 않습니다.
- 외부 아이콘 URL은 서버의 CSP 이미지 정책에 따라 차단될 수 있습니다.
- 여러 DB 작업은 단일 트랜잭션이 아니므로 중간 실패 시 일부만 반영될 수 있습니다.
- 메모리 기반 호출 제한은 서버 인스턴스 전체에 동일하게 적용되는 제한이 아닙니다.
- 심사자 코드 공유 방식은 운영 규모 확대 시 강화가 필요합니다.
- 심사자 판정 기반 보정은 표본 수·선정 편향·판정 일관성에 영향을 받습니다.

## 14. 테스트

테스트 파일이 있는 환경에서 실행합니다.

```bash
pytest -q tests
```

위 명령을 문서에 기재한 것이 테스트 통과를 의미하지는 않습니다.
실제로 수행한 테스트와 결과를 별도로 기록해야 합니다.

### 최종 제출 전 확인

- [ ] 메인 페이지가 500 오류 없이 열림
- [ ] `/api/health` 응답 확인
- [ ] 앱 이름 검색 후 후보 선택 확인
- [ ] 선택한 앱과 분석 대상의 일치 확인
- [ ] URL 입력과 잘못된 입력 처리 확인
- [ ] 분석 근거와 출처 URL의 일치 확인
- [ ] 근거 부족·조회 실패 안내 확인
- [ ] 분석 결과 저장 확인
- [ ] 제출 → 보완 요청 → 답변 → 심사자 확인 검증
- [ ] 작성자 코드 오류 및 심사자 인증 실패 처리 확인
- [ ] 코드와 Git 이력의 비밀키 노출 여부 확인

## 15. 향후 확장

- 새로운 바이브 코딩 도구와 AI 코딩 에이전트 조사
- 실제 서비스에서 확인할 수 있는 공개 근거 사례 수집

- 오탐 가능성과 한계 점검

- 오판 신고 및 이의제기 흐름 검토

자동 조사·자동 기준 갱신은 현재 구현된 기능이 아닙니다.

## 16. 오류 제보 방법

오류 수정 요청 시 다음 정보를 함께 제공합니다.

```text
입력값:
기대 결과:
현재 결과:
재현 순서:
배포 커밋 또는 배포 식별자:
관련 오류 로그:
```

예시:

```text
입력값: 육아기록
기대 결과: 여러 앱 후보 표시 후 사용자가 선택
현재 결과: 후보가 표시되지 않음
재현 순서: 메인 화면 → 앱 이름 입력 → 검색 버튼 클릭
배포 커밋 또는 배포 식별자: 해당 배포의 식별자
관련 오류 로그: 비밀값을 제거한 실제 오류 내용
```

API 키, 심사자 코드, 작성자 코드 등 민감한 값은 포함하지 않습니다.
